# 진단 방법론 v0.1

프로젝트: ICS Security Assessment Lab — Modbus TCP Security Assessment & Remediation

이 문서는 Day 1에 방법을 정의했다. 이후 Editor 시뮬레이터 실행과 Docker Runtime 연결은 사용자에게서 성공을 확인했으나, 버전·로그·화면 증거는 아직 저장소에 없다. 아래 진단 항목은 수행 결과가 아니다.

## 진행 흐름

| 단계 | 해야 할 판단 | 향후 산출물 | 증명하는 역량 |
| --- | --- | --- | --- |
| Scope | 대상·제외 대상·중단 조건 확정 | 범위와 자산 소유 확인 | 진단 범위 관리 |
| 환경 파악 / Discovery | 알려진 정보와 관찰한 정보를 분리 | 자산 목록, 접근 경로 | 제한 정보 기반 식별 |
| Service Identification | 포트로 추정한 서비스와 실제 응답 비교 | 서비스 및 버전 근거 | 검증 중심 분석 |
| Communication Analysis | 누가 요청하고 누가 응답하는지 설명 | 통신표와 PCAP | OT 프로토콜 이해 |
| Baseline | 정상 수위/상태/주기/예외 여부 기록 | 정상 PCAP과 화면 | 정상·이상 구분 |
| Checklist / Assessment | 가설별 관찰 방법과 판정 기준 작성 | 체크리스트 | 체계적인 진단 |
| Controlled Validation | 정상 범위 안에서 한 가지 조건만 바꿔 확인 | 시간·대상·변경·복원 증거 | 공정 보존과 검증 |
| Root Cause / Risk | 관찰, 원인, 추정 영향을 구별 | Finding 기록 | 위험 설명 |
| Remediation | 정상 통신을 유지하는 최소 통제 선택 | 구성 변경 근거 | 개선 설계 |
| Retest | 같은 조건에서 차단과 정상 운영을 함께 확인 | Before/After | 개선 효과 검증 |
| Report | 사실과 한계를 재현 가능하게 서술 | 기술 보고서 | 컨설팅 결과 전달 |

직접 만든 환경이므로 완전한 Black-Box 프로젝트라고 표현하지 않는다. 구축자 기록과 평가자 시작 정보를 분리한 제한 정보 기반 진단 연습이라고 설명한다. 평가자는 허용된 대상 범위부터 시작하고 자산명·버전·역할은 관찰 근거로 기록한다.

## 최소 평가 체크리스트

| ID | 확인할 가설 | 필요한 증거 | 판정 주의 |
| --- | --- | --- | --- |
| AS-01 | 등록된 자산과 실제 서비스가 일치하는가 | 허용 대상 목록, 관찰 주소·포트·응답 | 열린 포트만으로 제품/버전을 확정하지 않음 |
| MB-01 | 일반 Modbus TCP 값이 평문으로 관찰되는가 | 정상 요청/응답과 값 해석 | Modbus Security/TLS와 구별; CVE로 명명하지 않음 |
| AC-01 | 비인가 역할에서 PLC 서비스에 도달 가능한가 | 출발점·경로·응답 | TCP 연결과 읽기/쓰기 성공은 별개 |
| AC-02 | 비인가 역할의 제한된 쓰기가 수용되는가 | 변경 전후 값, 응답, PLC 실제 상태 | 후속 승인 범위의 가상 태그만; 현재 미실시 |
| MG-01 | 관리 서비스가 의도한 위치에만 노출되는가 | 실제 게시 주소와 연결 결과 | 설정 파일만으로 외부 차단 성공 판정 금지 |
| OP-01 | 조치 후 정상 HMI 동작이 유지되는가 | baseline 대비 polling·값·경보 | 차단만 성공하고 HMI가 끊기면 조치 실패 |

MB-01은 프로토콜 특성 관찰이고 AC-01/02는 배치·접근통제 문제의 가설이다. 같은 원인과 영향에 해당하는 항목을 여러 취약점으로 중복 집계하지 않는다. HMI 로그인은 PLC Modbus endpoint에 대한 인증을 자동으로 제공하지 않는다. 일반 Modbus와 보안 확장 구분은 [공식 규격 안내](https://www.modbus.org/modbus-specifications)를 참고한다.

## 정상 기준과 중단 조건

향후 baseline은 초기값 복원 후 60초 관찰을 최소 구간으로 제안한다. 요청/응답 쌍, 태그 값, 설정 주기, timeout/exception을 기록하고 정상 운전 요청 1회가 실제 펌프 상태에 어떻게 반영되는지 확인한다. 표본이 짧으므로 생산환경의 가용성 기준으로 일반화하지 않는다.

제한 검증은 실습 소유 자산과 사전에 정한 가상 태그에서만 수행한다. 한 번에 하나의 변경만 기록하고 변경 전 값과 복원 방법을 확보한다. 예상하지 못한 값, HMI 갱신 중단, 반복 timeout, 프로세스 재시작 또는 외부망 경로 발견 시 중단하고 마지막 정상 상태로 복원한다. 이번 작업에서는 이러한 요청을 전송하거나 도구·공격·자동화 코드를 작성하지 않는다.

## 위험도와 재검증

위험도는 접근 조건과 영향으로 설명한다. 가능성은 도달 가능 경로, 필요한 권한, 재현 여부로 판단하고 영향은 가상 운전 명령·상태·가시성의 변화로 판단한다. 증거가 없으면 미확인으로 남긴다. 실제 설비의 손상·인명 영향은 이 모델에서 검증할 수 없으므로 사실로 쓰지 않는다. 임의의 CVSS 수치 대신 근거가 있는 정성 평가와 잔여 위험을 사용한다.

재검증에서는 동일한 평가자 위치·대상·조건을 유지하고 정책만 바꾼다. 비인가 경로의 실패는 방화벽/경로 근거와 함께 설명하고, PLC가 단순히 꺼져서 실패한 것이 아닌지 HMI 정상 응답으로 확인한다. 네트워크 분리 후에도 허용된 HMI에서 가능한 쓰기와 평문 전송은 잔여 위험으로 기록한다.

## Evidence to save

- 공통 메타데이터: 증거 ID, 날짜·시간대, 출발/대상, 버전, 초기값, 수행 조건, 기대 결과, 관찰 결과, 판정, 한계.
- baseline/: 정상 PCAP, HMI 화면, 태그 대응표, 정상 주기 해석.
- assessment/: 자산·서비스 근거, 가설별 PCAP/화면, 패킷 번호, 가상 공정 변화.
- remediation/: 변경 전후 네트워크/정책 설명, 변경 이유, 복원 방법.
- retest/: 같은 조건의 차단 증거와 정상 HMI 동작 증거.
- 원본 PCAP과 편집한 발표 이미지를 구분한다. 비밀번호·토큰 등은 공개본에서 제거하고 원본 보관 위치를 구별한다. 파일 해시는 향후 증거 무결성 기록에 추가한다.

Finding에는 ID, 제목, 영향 자산, 조건, 관찰 사실, 증거 ID, 근본 원인, 공정 영향의 범위, 조치, 재검증 결과, 잔여 위험을 담는다. 다른 저장소의 스크린샷·성공 사례는 본인 실습 증거로 사용하지 않는다.

## What I need to understand

1. PLC는 제어 로직을 실행하고 HMI는 상태 표시와 운전 요청을 담당한다.
2. Modbus client/server 방향과 TCP 연결 방향을 설명할 수 있어야 한다.
3. Coil과 Register, 주소 표기와 wire offset, Function Code와 Exception을 구분한다.
4. 컨테이너 포트, 호스트 게시 포트, loopback, Docker 내부 네트워크를 구분한다.
5. 패킷이 보이지 않는 것과 통신이 없는 것은 다르다. 캡처 지점을 설명한다.
6. 화면의 버튼 제한과 PLC endpoint 접근통제는 서로 다르다.
7. 관찰 사실, 위험 가설, 검증 결과, 실제 공정에 대한 추정을 구별한다.
8. 보안조치는 비인가 접근 차단과 정상 운영 유지가 함께 확인되어야 한다.

## 전체 프로젝트의 향후 완료 기준

본인이 만든 공정과 주소 대응을 설명하고, 정상 PCAP에서 요청/응답을 해석하며, 최소 한 접근통제 문제를 증거로 평가하고, 개선 전후 및 정상 운영 유지 결과를 보고서로 남긴다. 재현에 필요한 버전·초기 상태·복원 절차도 남긴다. 이어서 공개 저장소 README, 제출용 요약본, 기술 보고서, 핵심 증거 링크를 갖추고 지원자가 이를 직접 설명할 수 있는지 점검한다. 이 모든 항목이 충족되어야 프로젝트 완료로 판정한다. 현재는 충족되지 않았다.
